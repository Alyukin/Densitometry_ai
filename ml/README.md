# ML: подготовка данных и обучение модели

Этап 2 проекта: от выгрузки `Densitometry_data` к обучаемому датасету и модели контроля
качества DXA. Здесь — результаты анализа данных, принятые решения и код подготовки.

Веб-сервис и API живут в корне репозитория и на этом этапе не меняются; модель
подключается в них через `backend/app/processing/` (см. корневой README).

## 1. Что в данных

### Объём

| | |
|---|---|
| исследований | 100 (папки в `НД_для_обучения/Исследования`) |
| файлов DICOM | 499 (~41 МБ) |
| уникальных снимков после дедупликации | **252** |
| из них размечено и годно для обучения | **246** |
| строк разметки | 100 (лист «Калибровка» в `разметка.xlsx`) |
| отдельная тестовая папка | 3 файла: `CR000000_ПОП`, `CR000000_ППОБ`, `CR000001_ЛПОБ` |

Состав уникальных снимков: позвоночник 99, бедро 153 (правое 74, левое 79).
Полных исследований (позвоночник + два бедра) — 74, только позвоночник — 21,
позвоночник + одно бедро — 4, только бедро — 1.

**Дубликаты.** Один и тот же снимок лежит в исследовании 2–5 раз: разные SOPInstanceUID,
разный тег `ExposedArea`, но побитово одинаковые пиксели. В исследовании из 13 файлов
реально 3 снимка. Дедупликация идёт по md5 пиксельного массива — иначе один и тот же
кадр попадёт и в train, и в validation.

**Состав исследования** (по полностью выгруженным исследованиям): позвоночник + два
бедра, либо часть из них. Больше трёх уникальных снимков не встречается.

### DICOM

Все снимки: `Modality=CR`, GE `Lunar Prodigy Advance`, ПО `18.41.005` / `18.50.082`,
8 бит, `MONOCHROME2`, Implicit VR Little Endian (без сжатия), размеры ≈233–405 × 248–300 px.

Что **отсутствует** и из-за чего пришлось принимать решения:

| Тег | Значение | Следствие |
|---|---|---|
| `BodyPartExamined`, `ViewPosition`, `Laterality` | пустые | область и сторону определяем по изображению |
| `PixelSpacing` | отсутствует | масштаб берём из ответа заказчика: 1.05 мм по Y, 0.6 мм по X |
| `PatientName/ID/BirthDate`, даты | `Anonymized` | сгруппировать по пациенту нельзя, группируем по исследованию |
| `StudyInstanceUID` в теге | ≠ имени папки | **разметка ссылается на имя папки**, join только по нему |

Последнее — главная ловушка: в Excel идентификаторы вида `2.25.*` (имена папок), а в
тегах — `1.2.643.5.*`. Совпадений между ними нет ни одного, join по тегу даёт 0 строк.

**Определение области.** Ширина кадра однозначно разделяет области: 300 px —
поясничный отдел, 280 px и уже — бедро. Проверено визуально на всей выборке и на
тестовой папке (`ПОП` → 300, `ППОБ`/`ЛПОБ` → 280).

**Определение стороны.** Эталон — имена файлов в папке «Для теста»: у правого бедра
(`ППОБ`) диафиз уходит влево по кадру (`shaft_x = 0.37`), у левого (`ЛПОБ`) — вправо
(`shaft_x = 0.65`). То же подтверждают 5 обучающих исследований, где размечено только
левое бедро: у всех `shaft_x > 0.5`. Внутри исследования сторона назначается сравнением
двух снимков между собой (устойчивее абсолютного порога): меньший `shaft_x` — правое.
На ~6% пар признак почти не разделяет (разница < 0.05) — такие кадры помечаются
`side_confidence < 0.3`.

### Разметка

Один лист, одна строка на исследование, значения 0/1, пусто = область не размечена:

| Область | Колонки-компоненты | Итог |
|---|---|---|
| Позвоночник | корректная укладка; ось выровнена (до 5°); посторонние предметы/артефакты | J |
| Правое бедро | позиционирование/ротация; корректность ROI | K |
| Левое бедро | позиционирование/ротация; корректность ROI | L |

Компоненты один в один ложатся на закрытые списки заказчика:
«Некорректная укладка», «Не выравнена ось позвоночника», «Присутствуют посторонние
предметы» для позвоночника и «Некорректная укладка», «Некорректная область интереса»
для бедра.

### Классы и дисбаланс

На уровне исследований:

| Область | норма | нарушение | не размечено |
|---|---|---|---|
| Позвоночник | 67 | 32 | 1 |
| Правое бедро | 53 | 19 | 28 |
| Левое бедро | 56 | 22 | 22 |

Исследований хотя бы с одним нарушением — 50 из 100.

По типам нарушений (исследований):

| Нарушение | Позвоночник | Бедро (прав.) | Бедро (лев.) |
|---|---|---|---|
| Некорректная укладка | 6 | 17 | 19 |
| Не выравнена ось | 10 | — | — |
| Посторонние предметы | 17 | — | — |
| Некорректная ROI | — | 3 | 4 |

Главная проблема — редкие классы: «Некорректная область интереса» встречается 7 раз на
оба бедра, «Некорректная укладка» позвоночника — 6 раз. Для них отдельные метрики будут
крайне неустойчивы (95% ДИ шириной почти во весь диапазон).

### Найденные проблемы

1. **Разметка на уровне исследования, а модель работает с кадрами.** Для бедра метка
   зависит от стороны: у 14 исследований из 72 метки левого и правого бедра различаются,
   то есть ошибка определения стороны сразу даёт неверную метку.
2. **3 расхождения между «Итогом» и компонентами** (строки 8, 13 — Итог=1 без единого
   отмеченного компонента; строка 37 — Итог=0 при отмеченной оси). Разбираются правилами
   R3/R4 в `dxa/label_qc.py` — см. раздел 2.1.
3. **Сводный блок в самом файле разметки устарел** (там 50/26 по позвоночнику против
   фактических 67/32) — ориентироваться на него нельзя.
4. **22 исследования без снимков бедра и 1 без позвоночника**, поэтому часть колонок
   пуста. Это не ошибка, но нужно учитывать при расчёте покрытия.
5. **Единичные нетипичные кадры**: два снимка 248 px с эндопротезом (комментарии
   «эндопротезирование ТБС»), несколько сильно обрезанных кадров. Их видно на
   контактных листах.
6. **Комментарии эксперта** (23 строки: «сколиоз», «перелом», «не верная разметка»,
   «требует внимание») содержат информацию, которой нет в колонках; сколиоз объясняет
   часть нарушений оси и может пригодиться при разборе ошибок модели.
7. Ни одного полного дубля и ни одной пары похожих снимков **между разными
   исследованиями** не найдено (косинусная близость 32×32, порог 0.97) — явной утечки
   «один пациент в двух исследованиях» не видно, но гарантировать этого нельзя:
   персональные данные обезличены, повторный приём одного пациента отследить нечем.

## 2. Как организована подготовка данных

```
python -m dxa.build_dataset --data-root /path/Densitometry_data --out data/processed
python -m dxa.contact_sheet --data data/processed --out qa     # листы для проверки глазами
```

На выходе:

| Файл | Что внутри |
|---|---|
| `manifest.csv` | все файлы DICOM: теги, md5, область, сторона, пометка дубликата |
| `dataset.csv` | по одному уникальному снимку на строку: метка, источник метки, фолд |
| `images/*.png` | 8-битные PNG (пиксели не меняются, только контейнер) |
| `report.md`, `stats.json` | отчёт по данным и все цифры из раздела 1 |
| `labels_clean.csv` | очищенная разметка для обучения |
| `label_fixes.csv` | журнал автоправок: правило, что было, что стало, основание |
| `manual_review.csv` | что машина решить не может — на эксперта |
| `label_qc_report.md` | отчёт по проверке разметки |
| `qa/*.png` | контактные листы: позвоночник, правое бедро, левое бедро, ненадёжная сторона |

Ключевые решения, зашитые в код:

- **Дедупликация по пикселям** внутри исследования, в обучение идут только уникальные кадры.
- **Join по имени папки**, а не по `StudyInstanceUID` из тега.
- **Источник метки фиксируется** в колонке `label_source`:
  `direct` — сторона определена по изображению (237); `label_side` — сторона взята из
  разметки (5); `side_agnostic` — стороны различимы слабо, но метки совпадают (4);
  `ambiguous_side` (2), `conflict` (1), `unlabeled` (3) — исключаются из обучения.
- **Фолды по исследованиям** (group k-fold) со стратификацией по сочетанию
  «позвоночник × бедро» — один пациент не может попасть и в train, и в validation.
- Никакой перезаписи исходных данных: папка с выгрузкой только читается.

### 2.1. Проверка разметки

`dxa/label_qc.py` прогоняет разметку через набор правил до сборки датасета.
**Исходный `разметка.xlsx` не изменяется** — он только читается; для обучения создаётся
отдельный `labels_clean.csv`.

Принцип: автоматически исправляется только то, для чего есть проверяемое основание
в самих данных. Если два экспертных поля противоречат друг другу и нельзя сказать, какое
верное, строка не «чинится», а исключается из обучения и уходит в `manual_review.csv`.

| Правило | Что | Основание |
|---|---|---|
| R1 | нормализация значений ('0'/'1' → int, strip у UID) | формат хранения, смысл не меняется |
| R2 | Итог пуст, компоненты есть → Итог = max(компонентов) | «Итог» по устройству листа — сводка компонентов; равенство выполняется в 246 из 249 областей |
| R3 | Итог = 1, все компоненты 0 → класс 1, **вид нарушения неизвестен** | заключение эксперта сохраняется; вид нарушения не выдумывается — головы нарушений маскируются (`violations_known = 0`) |
| R4 | Итог = 0, но компонент = 1 → **исключить из обучения** | поля прямо спорят о классе, выбрать можно только догадкой |
| R5 | значение вне {0, 1} → ячейка считается пустой | |
| R6 | повтор StudyInstanceUID → исключить | непонятно, какая строка актуальна |
| R7 | сверка со снимками: разметка без снимка → отбросить; снимок без разметки → не учить | |
| R8 | один снимок бедра + размечена одна сторона → сторона из разметки | эксперт размечал тот снимок, который есть; это наблюдение, а не вывод |
| R9 | пара бёдер с неразличимым положением диафиза: метки разные → исключить обе (R9a); метки одинаковые → оставить (R9b) | при одинаковых метках перестановка сторон ничего не меняет |

Результат на текущей выгрузке:

| | |
|---|---|
| строк разметки (исследование × область) | 249 |
| годных для обучения | 248 |
| из них без вида нарушения (R3) | 2 |
| исключено по противоречию (R4) | 1 |
| автоматических исправлений | 4 |
| на ручную проверку | 4 |

Что попало на ручную проверку:

| Приоритет | Правило | Строка | Что решить | Комментарий эксперта |
|---|---|---|---|---|
| высокий | R4 | 37 | что верно: Итог = 0 или отмеченное «не выравнена ось» | «перелом» |
| высокий | R9a | 71 | какой снимок бедра правый, а какой левый (разница shaft_x 0.048, метки сторон разные) | — |
| средний | R3 | 8 | какое нарушение соответствует Итогу = 1 | «сколиоз» |
| средний | R3 | 13 | то же | «Сколиоз, не верная разметка» |

Эти четыре ответа — единственное, что нужно от эксперта, чтобы разметка стала полностью
непротиворечивой. Обучению они не мешают: строка 37 и два снимка строки 71 просто
исключены, строки 8 и 13 учатся только по классу качества.

## 2.2. Baseline без обучения

До нейросети реализован рабочий контроль качества на явных правилах ТЗ: измерения по
изображению (ось позвоночника в градусах, поля ROI в сантиметрах, выступ малого
вертела, посторонние предметы) плюс пороги. Он уже встроен в сервис как процессор
`rulebased` и служит точкой отсчёта для модели.

Код измерений — `backend/app/processing/dxaqc/` (без FastAPI и torch, поэтому
используется и сервисом, и офлайн-оценкой). Оценка и калибровка — `ml/baseline/`.

Кратко по качеству (out-of-fold, те же фолды, что у модели):

| Область | качество BA | лучший класс нарушения | худший класс | macro-F1 |
|---|---:|---|---|---:|
| Позвоночник | 0.61 | укладка BA 0.70 / AUC 0.82 | посторонние предметы BA 0.63 / AUC 0.71 | 0.341 |
| Бедро | 0.69 | область интереса BA 0.69 / AUC 0.87 | укладка BA 0.66 / AUC 0.68 | 0.319 |

Все проверки раздела 2.3 ТЗ реализованы и считаются на каждом снимке. Часть из них
помечена как справочные (`decides=False`): они показываются пользователю с измеренной
величиной и порогом ТЗ, но не формируют `violation_type`, потому что на выгрузке с
6–9 позитивами не отделяют нарушение от нормы. Это флаг в описании правила, а не
удалённая проверка.

Полный отчёт, включая покрытие раздела 2.3 ТЗ, методику измерения оси, выведенную из
рисунка 2, два расхождения ТЗ с фактической разметкой и предел подхода —
[ml/baseline/REPORT.md](baseline/REPORT.md).

## 3. План обучения

### Постановка

Одна модель на обе области: общий бэкбон + 7 бинарных голов, лосс считается только по
головам своей области (маска). Головы:

```
spine_quality, spine_position, spine_axis, spine_foreign
femur_quality, femur_position, femur_roi
```

Область определяется до модели (по ширине кадра), поэтому отдельная голова на
классификацию области не нужна — но её предсказание всё равно проверяется на контактных
листах.

Почему так, а не три отдельные модели: размеченных кадров 246, при раздельном обучении
на редкие классы приходится по 5–7 примеров. Общий бэкбон переносит признаки между
областями, а маскированный лосс не смешивает задачи.

Маска лосса решает и вторую задачу: для строк, где эксперт забраковал область, но не
указал вид нарушения (правило R3), головы нарушений выключаются, а голова качества
учится. Так класс не теряется и при этом модели не сообщается, будто нарушений нет.

### Запуск baseline

Одной командой — зависимости, проверка разметки, сборка датасета, 5 фолдов, метрики:

```bash
bash ml/train.sh /путь/к/Densitometry_data
```

Путь можно не указывать, если `Densitometry_data` лежит рядом с репозиторием.
Скрипт ничего не пишет в исходные данные. На H200 полный прогон — единицы минут.
Настройки через переменные окружения: `EPOCHS`, `BACKBONE`, `BATCH`, `OUT_RUN`.

Результат:

| Файл | Что внутри |
|---|---|
| `runs/cnn/metrics.json` | sensitivity, specificity, balanced accuracy, F1, ROC AUC, PR AUC + 95% ДИ по каждой из 7 голов |
| `runs/cnn/oof_predictions.csv` | out-of-fold предсказания по каждому снимку |
| `runs/cnn/fold*.pt` | веса пяти фолдов (в инференсе усредняются) |
| `data/processed/report.md` | отчёт по данным |
| `data/processed/manual_review.csv` | спорные места разметки |
| `qa/*.png` | контактные листы для проверки глазами |

Если нужно по шагам:

```
pip install -r requirements-train.txt
python -m dxa.build_dataset --data-root /путь/к/Densitometry_data --out data/processed
python -m train.train --data data/processed --out runs/cnn --backbone resnet18 --epochs 40
```

- бэкбон `resnet18` (ImageNet), альтернативы — `resnet34`, `efficientnet_b0` и
  `xrv-densenet121` — веса TorchXRayVision, обученные на рентгенограммах (вход
  одноканальный, нормировка переключается сама — и при обучении, и в `train.predict`);
- вход 384×320, снимок в оттенках серого дублируется в 3 канала;
- `BCEWithLogits` с `pos_weight` по каждой голове — компенсация дисбаланса;
- 5 фолдов по исследованиям, выбор эпохи по среднему ROC AUC двух голов качества;
- на выходе `oof_predictions.csv`, `metrics.json` (sensitivity, specificity, balanced
  accuracy, F1, ROC AUC, PR AUC + 95% ДИ бутстрэпом), `config.json` и веса фолдов.

**Аугментации выбраны под смысл меток.** Повороты меняют угол оси позвоночника, а порог
нарушения — 5°, поэтому для позвоночника вращение отключено, для бедра ограничено 3°.
Горизонтальное отражение превращает левое бедро в правое: анатомически корректно, но по
умолчанию выключено (`--hflip-femur`), потому что на нём же держится определение стороны.
Остальное — небольшие сдвиг, масштаб и яркость.

### Какой бэкбон брать: линейный зонд

```
python -m train.probe --data data/processed
```

Бэкбон заморожен, поверх — логистическая регрессия на каждую задачу; фолды и правило
выбора порога те же, что у правил. Минуты на CPU вместо часов обучения — и ответ, видит
ли бэкбон в наших задачах что-то сам по себе. Контроль — та же архитектура со
случайными весами: разница с ней и есть вклад предобучения.

Первый прогон (ROC AUC, out-of-fold):

| | правила | XRV 384×320 | XRV, случайные веса |
|---|---:|---:|---:|
| бедро: есть нарушение | 0.74 | 0.70 | 0.50 |
| бедро: укладка | 0.68 | 0.67 | 0.58 |
| бедро: область интереса | 0.87 | 0.80 | 0.69 |
| позвоночник: ось | 0.78 | 0.39 | 0.60 |

На бедре XRV уже без дообучения держится вровень с правилами (macro-F1 0.316 против
0.319), и это заслуга предобучения — случайные веса дают 0.50. На позвоночнике — нет:
наклон оси — геометрия, а глобальное усреднение признаков её теряет. Колонку ImageNet
этот прогон не посчитал: здесь закрыт `download.pytorch.org`, на машине с доступом
она досчитается той же командой.

### Оценка

Основная метрика — по кадрам, отдельно для позвоночника и бедра; редкие типы нарушений
считаются, но интерпретируются с оглядкой на ширину ДИ. Порог — 0.5: `pos_weight`
уравновешивает классы, и 0.5 — естественная рабочая точка. По OOF порог не подбирается:
подбор на тех же данных, на которых считаются BA и F1, их завышает. Если порог всё же
нужен свой, его выбирают вложенной кросс-валидацией, как в `train/probe.py`, и передают
в `predict.py` через `--thresholds`.

Дополнительно стоит считать метрику на уровне исследования (нарушение хотя бы в одном
кадре) — она ближе к тому, как сервис используют.

**Метрики локализации** (Dice, IoU, расстояние между ключевыми точками) и пропускная
способность (время обработки, доля успешно обработанных файлов) реализованы в том же
`train/metrics.py` и считаются для baseline командой `make localization`. Модель, когда
она появится, оценивается теми же функциями — цифры будут сравнимы напрямую. Как
устроена «истина» для локализации, когда экспертных масок нет, описано в
[baseline/REPORT.md](baseline/REPORT.md).

### Инференс

```
python -m train.predict --input /path/studies --models runs/cnn --out result.csv --xlsx
```

Колонки строго по ТЗ плюс разрешённая заказчиком `quality_prob`:

```
path_to_study, study_uid, image_uid, anatomical_region, quality_class,
violation_type, processing_status, time_of_processing, quality_prob
```

`anatomical_region` и `violation_type` заполняются значениями из закрытых списков
заказчика, `quality_class` — 0/1, несколько нарушений через `;`.

### Что нужно поправить в сервисе при подключении модели

Mock сейчас отдаёт англоязычные коды (`lumbar_spine`, `acceptable`, `spine_axis_tilt`).
После подключения модели значения должны стать теми, что в закрытых списках, и добавиться
колонка `quality_prob`: правки в `backend/app/processing/`, `backend/app/services/export.py`
и словарях `frontend/src/utils/format.ts`.

### Риски и что с ними делать

| Риск | Что делаем |
|---|---|
| Данных мало (~220 кадров, редкие классы по 5–7) | перенос весов, 5-fold CV вместо одного сплита, ДИ ко всем метрикам, консервативные аугментации |
| Ошибка определения стороны → неверная метка бедра | сторона из сравнения пары, `side_confidence`, спорные кадры исключаются, контактные листы для проверки экспертом |
| Разметка на уровне исследования | фиксируем источник метки, при росте датасета просим поимённую разметку по снимкам |
| Расхождения «Итог» vs компоненты | выписаны в отчёт, нужен ответ разметчика |
| Скрытая утечка «один пациент — два исследования» | проверка на дубли и near-duplicate между исследованиями; сплит по исследованиям |
| Перекос по аппарату | вся выгрузка — один Lunar Prodigy Advance; на другом аппарате модель не проверена, это ограничение нужно указывать в отчёте |
