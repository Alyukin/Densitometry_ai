# Состояние сервиса — подробно

Развёрнутое описание того, что сейчас умеет Densitometry AI: как принимается решение,
как устроена проверка специалистом, что выгружается и что делать, если что-то не
заводится. Короткая версия для запуска — в [README.md](README.md), качество baseline и
метрики — в [ml/baseline/REPORT.md](ml/baseline/REPORT.md).

Сейчас работает baseline на явных правилах: измерения по изображению (ось позвоночника
в градусах, поля ROI в сантиметрах, малый вертел, посторонние предметы) плюс пороги из
ТЗ. Нейросети нет, она подключается отдельным процессором и сравнивается с baseline на
тех же метриках.

## Запуск

Нужен Docker с плагином Compose v2 (`docker compose version`).

```bash
docker compose up --build
```

- Сайт: http://localhost:8080
- Документация API (Swagger): http://localhost:8080/docs

Остановить — `docker compose down`, удалить данные — `docker compose down -v`.

Настройки менять необязательно. Если нужно — `cp .env.example .env`, там всё с
комментариями (порты, число параллельных обработок, лимиты).

Тестовые файлы лежат в `samples/`: перетащите `samples/demo_studies.zip` на сайт.

## Что умеет сайт

Загрузить файлы, папку или ZIP → нажать «Обработать» → увидеть статус и результат →
скачать CSV или XLSX. Файлы сами группируются в исследования по `StudyInstanceUID`,
не-DICOM отклоняются с указанием причины. Есть пакетная обработка выбранных или всех
новых исследований и сводная выгрузка по всем.

Повторная загрузка дубликатов не создаёт: снимок, который уже есть в сервисе (тот же
`SOPInstanceUID`), отклоняется с причиной. Новые снимки уже загруженного исследования
добавляются к нему, и оно снова ждёт обработки, — так исследование, загруженное по
частям, остаётся одним. Пока исследование обрабатывается, добавить в него снимки нельзя.

У каждого снимка показывается разметка поверх изображения (ось позвоночника, контур
бедренной кости, ориентиры, найденные посторонние предметы) — кнопка «Без разметки»
переключает на исходный кадр. Под результатом перечислены все проверки с измеренными
значениями и порогами.

Кроме CSV и XLSX, результат выгружается в **DICOM SR** (заключение для PACS) и
**ZIP-пакетом**: SR, вторичная серия с наложенной разметкой и обе таблицы разом.

## Проверка специалистом

Под каждым снимком — «Подтвердить» и «Исправить». Врач либо соглашается с вердиктом
сервиса, либо отмечает нарушения сам; список нарушений ограничен тем же закрытым
перечнем, что и у модели, — своё вписать нельзя.

Автоматический вердикт при этом **не переписывается**: решение врача хранится в
отдельных полях. Поэтому всегда видно, что предложил сервис и что решил человек, а
метрики модели не оказываются посчитанными по исправленным данным. По той же причине
выгрузка по умолчанию отдаёт автоматический вердикт; чтобы получить утверждённый
врачом, нужен параметр `?source=reviewed`. В XLSX есть отдельный лист `review`, где обе
версии стоят рядом.

Повторная обработка решение врача не стирает: оно переносится на новый результат того
же снимка. Если новый вердикт сервиса совпал с решением врача, проверка считается
подтверждением, если нет — исправлением, а решение врача остаётся тем же. Перенести
нельзя, только если снимок теперь не обработался или область определилась другая; тогда
решение врача записывается в предупреждения исследования. Пока исследование в очереди
или обрабатывается, подтверждать и исправлять нельзя.

## API

Полное описание — в Swagger. Кратко:

| Метод | Путь | Что делает |
|---|---|---|
| GET | `/health` | Сервис жив, какой процессор используется |
| POST | `/api/v1/studies/upload` | Загрузить DICOM или ZIP (поле `files`) |
| GET | `/api/v1/studies` | Список исследований |
| GET | `/api/v1/studies/{id}` | Одно исследование и его снимки |
| DELETE | `/api/v1/studies/{id}` | Удалить исследование |
| POST | `/api/v1/studies/{id}/process` | Запустить обработку |
| GET | `/api/v1/studies/{id}/status` | Статус и прогресс |
| GET | `/api/v1/studies/{id}/result` | Результат в JSON |
| GET | `/api/v1/studies/{id}/download?format=csv\|xlsx&source=auto\|reviewed` | Скачать результат |
| GET | `/api/v1/studies/{id}/sr` | Заключение в виде DICOM SR |
| GET | `/api/v1/studies/{id}/package` | ZIP: SR + вторичная серия с разметкой + таблицы |
| GET | `/api/v1/studies/{id}/images/{image_id}/preview` | PNG-превью снимка |
| GET | `/api/v1/studies/{id}/images/{image_id}/overlay` | PNG с найденными структурами |
| POST | `/api/v1/studies/{id}/images/{image_id}/review` | Подтвердить или исправить вердикт |
| POST | `/api/v1/batch/process` | Пакетная обработка |
| GET | `/api/v1/batch/download?format=csv\|xlsx` | Сводный файл |

Статусы: `uploaded → queued → processing → completed | failed`.

Пример:

```bash
curl -F "files=@samples/demo_studies.zip" http://localhost:8080/api/v1/studies/upload
curl -H 'Content-Type: application/json' -d '{"all_pending": true}' \
     http://localhost:8080/api/v1/batch/process
curl -o result.xlsx "http://localhost:8080/api/v1/batch/download?format=xlsx"
curl -o report.zip  "http://localhost:8080/api/v1/studies/<id>/package"
curl -H 'Content-Type: application/json' \
     -d '{"action":"correct","violation_type":["Не выравнена ось позвоночника"],"reviewed_by":"Иванов И.И."}' \
     "http://localhost:8080/api/v1/studies/<id>/images/<image_id>/review"
```

Проверить всё сразу: `make smoke` (или `bash scripts/smoke_test.sh`).

## Результат

Одна строка на снимок, колонки по ТЗ плюс `quality_prob` (разрешена заказчиком):

```
path_to_study,study_uid,image_uid,anatomical_region,quality_class,violation_type,processing_status,time_of_processing,quality_prob
```

Форматы значений — по ТЗ (п. 2.5): `quality_class` — целое 0 или 1 (пусто, если область
не оценена), `processing_status` — `Success` или `Failure`, `time_of_processing` — секунды.
Значения `anatomical_region` и `violation_type` — строго из закрытых списков заказчика:

* позвоночник: «Некорректная укладка», «Не выравнена ось позвоночника», «Присутствуют посторонние предметы»;
* бедро: «Некорректная укладка», «Некорректная область интереса».

Несколько нарушений перечисляются через `;`. В XLSX есть ещё лист `checks` — по строке
на каждую проверку: измеренная величина, критерий, порог ТЗ, вердикт по букве ТЗ и
участвует ли проверка в итоговом решении.

## Как принимается решение

Каждое нарушение — это порог на величине, измеренной по изображению. В ответе API
(`details.checks`) для каждой проверки видно измеренное значение, порог, сработала ли
она и откуда взят критерий: `ТЗ` или `разметка` (подобран по размеченной выгрузке,
потому что в ТЗ названа проверка, но не названо число).

Пример для снимка позвоночника:

```
[ ] Верхние края подвздошных костей в кадре: 2.64 × ширины столба   (порог 1.53)
[ ] Наклон оси по боковым границам столба: 1.8°                     (порог 1.88°)
[X] Тонкие яркие структуры вне кости: 162.00 ед. яркости            (порог 56.65)
[·] Наклон оси позвоночника (методика ТЗ, рис. 2): 4.1°   по букве ТЗ: в норме (до 5°)
[·] Позвонков в кадре: 7.00 шт                            справочно, в вердикт не входит
```

Строки, помеченные `[·]`, — справочные: проверка требуется ТЗ, считается и показывается
вместе с порогом из ТЗ, но не формирует `violation_type`, потому что на размеченной
выгрузке не отделяет нарушение от нормы. Все проверки раздела 2.3 ТЗ выполняются;
что из них решает, а что справочно — в отчёте.

Три исхода, кроме обычного вердикта (почему так — [questions.md](questions.md), З3):

* **`Failure`** — файл не открывается или не разбирается как DICOM. Такой файл не
  отбрасывается при загрузке: у него есть строка в выгрузке с причиной.
* **Нестандартные данные** — DICOM открылся, но это не снимок позвоночника или бедра
  (нет изображения, другая модальность или часть тела, цветной кадр, не похож на
  снимок денситометра, нет кости). `Success`, область, класс и `quality_prob` пустые,
  причина видна в интерфейсе и в SR.
* **Структуры не найдены** — кость в кадре есть, но бедро не разбирается на диафиз и
  вертелы или не выделяется позвоночный столб. Вердикт «Некорректная укладка» с
  `quality_prob` 0.51: то, что по ТЗ должно быть видно, не найдено.

Качество baseline на отложенных данных, метрики локализации (Dice / IoU / расстояние
между ключевыми точками), покрытие раздела 2.3 ТЗ, найденные расхождения ТЗ с
фактической разметкой и предел подхода — в
[ml/baseline/REPORT.md](ml/baseline/REPORT.md).

## Как устроено

- `frontend/` — React + Vite, раздаётся через nginx, он же проксирует запросы к API.
- `backend/` — FastAPI. Файлы и база SQLite лежат в Docker-томе `densitometry-data`.
  Из DICOM сохраняются только технические метаданные, без персональных данных.
- Обработка идёт в фоновых потоках внутри процесса API, поэтому backend запускается
  одним процессом. Если сервис перезапустить, незавершённые задачи встанут в очередь заново.

## Данные и обучение модели

Анализ выгрузки `Densitometry_data`, подготовка датасета и обучение — в папке `ml/`
(там же отчёт по данным и план обучения): [ml/README.md](ml/README.md).

## Как подключить модель и сравнить её с baseline

1. В `backend/app/processing/` написать класс на основе `BaseProcessor` с методами
   `load()` (загрузка весов) и `predict(image)` (обработка одного снимка).
2. Зарегистрировать его в `registry.py` и указать `PROCESSOR_BACKEND=<имя>` в `.env`.
3. Добавить зависимости в `backend/requirements.txt`, при необходимости раскомментировать
   GPU-секцию в `docker-compose.yml`.

Сайт, API и выгрузку менять не нужно: baseline и модель — взаимозаменяемые процессоры.
Метрики считаются одним и тем же кодом (`ml/train/metrics.py`) на одних и тех же фолдах,
поэтому цифры сравнимы напрямую. Подробности — в комментариях
`backend/app/processing/base.py`.

Доступные процессоры: `rulebased` (по умолчанию) и `mock` (тестовые результаты без
обработки изображения).

## Разработка без Docker

Нужны Python 3.12 и Node.js 22.

```bash
make install        # зависимости
make dev-backend    # API на :8000
make dev-frontend   # сайт на :5173
make test           # тесты backend и метрик
make localization   # метрики локализации по ТЗ
```

Тесты в контейнере — `make test-docker`. Все команды есть в `make help`.

## Если сайт открывается, а запросы к API отдают 502

В журнале frontend при этом «backend could not be resolved» — значит в этой установке
Docker контейнеры не находят друг друга по имени. Проверить:

```bash
docker compose exec frontend sh -c 'cat /etc/resolv.conf; nslookup backend; wget -qO- http://backend:8000/health'
```

Если `nslookup backend` не отвечает, обойти DNS можно, прописав в `.env` одно из:

```bash
BACKEND_URL=http://host.docker.internal:8000   # через хост по опубликованному порту
BACKEND_URL=http://<IP backend>:8000           # docker compose exec backend hostname -i
```

После правки — `docker compose up -d --force-recreate frontend`. Первый вариант не
требует DNS вовсе: адрес берётся из `/etc/hosts`, куда его кладёт `extra_hosts`.

## Ограничения

- Результаты тестовые, это не медицинское заключение.
- Входа по паролю нет — сервис рассчитан на закрытый контур. По этой же причине в
  поле «кто проверил» пишется то, что ввели: подписи врача сервис не удостоверяет.
- SQLite и очередь в процессе рассчитаны на один экземпляр backend.
- Персональные данные в базе не хранятся: из DICOM берутся только технические теги.
  Идентификаторы пациента попадают только в DICOM SR — они читаются из исходного файла
  в момент выгрузки, иначе отчёт не встанет в PACS к нужному исследованию.
