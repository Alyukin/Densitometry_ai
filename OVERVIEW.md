# Densitometry AI — полный обзор проекта

Состояние на 28.09.2026. Один документ обо всём: цель, данные, архитектура, что пробовали
и что это дало, какие решения приняты и что решается сейчас. Подробности по каждой
части — в файлах, на которые даны ссылки.

---

## 0. Коротко

- **Что это.** Сервис контроля качества DXA-исследований (денситометрия): принимает DICOM,
  по каждому снимку поясничного отдела позвоночника или проксимального отдела бедра
  говорит, годен ли он, какие нарушения укладки найдены и почему — с измеренной
  величиной и порогом рядом с каждым выводом.
- **Что работает.** Полный сервис (сайт, API, очередь, выгрузки CSV/XLSX, DICOM SR,
  проверка врачом) на **правилах ТЗ**: измерения по изображению + пороги. Вердикт на
  502 из 502 файлов выгрузки, 43 мс на снимок.
- **Качество правил** (out-of-fold, 246 снимков): macro-F1 позвоночник **0.341**, бедро
  **0.319**; ROC AUC класса качества 0.69 и 0.74.
- **Нейросеть.** Проверено пять подходов (зонд на замороженной сети, ResNet18 v1, три
  конфигурации протокола v2) и гибрид правил с лучшей моделью. **Ни один не превзошёл
  правила**: вердикт выносят правила. Причина — объём данных: 246 снимков, в редких
  классах 6–9 нарушений.
- **Модель в сервисе — вторым мнением.** Для бедра рядом с проверками правил показывается
  оценка замороженного DenseNet121 с её точностью; в вердикт и выгрузку она не входит.
- **Сдача.** Сервис прогнан в Docker по «Для теста» и по всей выгрузке, формат п. 2.5 без
  нарушений; пакет для целевой машины собирается `make package`.

## 1. Цель и требования

### Задача по ТЗ

Автоматическая оценка качества выполнения DXA-исследования по двум областям:

| Область | Что проверяется (раздел 2.3 ТЗ) | Закрытый список нарушений |
|---|---|---|
| Поясничный отдел позвоночника | укладка: внизу видны верхние края подвздошных костей, вверху — половина тела Th12 (рис. 1); ось позвоночника, наклон до 5° (рис. 2); нет посторонних предметов, артефактов, наложений (рис. 3) | «Некорректная укладка», «Не выравнена ось позвоночника», «Присутствуют посторонние предметы» |
| Проксимальный отдел бедра | видны большой вертел, шейка, седалищная кость (рис. 4); нет ротации — по малому вертелу: корректно / переротация / недоротация (рис. 5); область интереса с запасом 3 см сверху-снизу и 2 см справа-слева (рис. 6) | «Некорректная укладка», «Некорректная область интереса» |

### Выход (п. 2.5 ТЗ) — одна строка на снимок

```
path_to_study, study_uid, image_uid, anatomical_region, quality_class,
violation_type, processing_status, time_of_processing, quality_prob
```

- `quality_class` — целое 0/1; `processing_status` — `Success` / `Failure`;
  `time_of_processing` — секунды; несколько нарушений — через `;`.
- `quality_prob` — разрешён заказчиком дополнительно (ответ на вопрос 8).
- `anatomical_region` — два значения без проекции (ответ на вопрос 15), сторона бедра в
  выгрузку не входит.
- `Failure` — только если файл не открывается или не разбирается как DICOM (ответ
  заказчика 23.09).

### Технические требования

- До 3 изображений в исследовании, не больше 3 минут на исследование.
- Воспроизводимость (один файл — один вердикт), независимость от персональных тегов.
- Дополнительно: DICOM SR и дополнительные серии, автоматическая коррекция разметки с
  подтверждением специалиста.
- Метрики: классификация (Se, Sp, BA, F1, ROC/PR AUC, macro-F1), локализация (Dice, IoU,
  расстояние между ключевыми точками), пропускная способность.
- Закрытый тест: папка «Для теста», целевая машина 2 × H200, 44 CPU, 256 ГБ.

Особенности, из-за которых пришлось принимать решения:

- **Дубли:** один снимок лежит в исследовании 2–5 раз с разными SOPInstanceUID и
  одинаковыми пикселями — дедупликация по md5 пикселей, иначе утечка между фолдами.
- **Пустые теги** `BodyPartExamined`, `ViewPosition`, `Laterality`, нет `PixelSpacing` —
  область определяется по ширине кадра (300 px — позвоночник, 280/248 px — бедро),
  сторона бедра — по положению диафиза, пиксель 1.05 × 0.60 мм (данные заказчика).
- **Разметка ссылается на имя папки (`2.25.*`), а не на StudyInstanceUID в тегах
  (`1.2.643.*`)** — join только по имени папки.
- **Разметка на уровне исследования**, а модель работает со снимками: для бедра метка
  зависит от правильно определённой стороны (у 14 из 72 исследований метки бёдер
  различаются).
- UID сканера формально нарушают стандарт (компоненты с ведущим нулём) — pydicom
  предупреждает, на работу не влияет.

## 3. Архитектура

### Схема

```
браузер ──► nginx (frontend, :8080) ──► FastAPI (backend, :8000)
                                          │
              загрузка ─► UploadService ──┤ группировка по StudyInstanceUID,
                                          │ не-DICOM → строка Failure, дедупликация
                                          ▼
                                   SQLite + файлы (том densitometry-data)
                                          │
        «Обработать» ─► TaskRunner (потоки в процессе API)
                                          │
                                          ▼
                                     pipeline ─► intake (заголовок DICOM:
                                          │       Failure / нестандартные данные)
                                          ▼
                                     процессор: rulebased (+ второе мнение, бедро) | mock
                                          │
                                          ▼
                     результат: CSV / XLSX / DICOM SR / ZIP-пакет / PNG с разметкой
                     + проверка врачом (решение хранится отдельно от вердикта сервиса)
```

### Backend (`backend/app/`)

| Модуль | Что делает |
|---|---|
| `main.py` | приложение FastAPI, Swagger без интернета, перезапуск прерванных задач при старте |
| `api/routes/` | `studies` (загрузка, статус, результат, выгрузки, превью, разметка, проверка врачом), `batch` (пакетная обработка и сводная выгрузка), `health` |
| `services/upload.py` | потоковая загрузка файлов и ZIP, отсев служебных файлов и документов; снимок, уже загруженный ранее (тот же SOPInstanceUID), отклоняется, новые снимки существующего исследования добавляются к нему |
| `services/pipeline.py` | обработка исследования по снимкам, прогресс, лимит 180 с; при повторной обработке решение врача переносится на новый результат |
| `services/task_runner.py` | пул потоков; интерфейс `submit(study_id)` заменяется на Celery/RQ без изменения остального |
| `services/review.py` | подтверждение / исправление вердикта врачом по тому же закрытому списку; автоматический вердикт не переписывается |
| `services/export.py` | CSV/XLSX по п. 2.5 ТЗ; в XLSX ещё листы `checks` (все проверки с порогами) и `review` |
| `services/dicom_sr.py`, `package.py`, `overlay.py` | Comprehensive SR (проверен `dsrdump`), вторичная серия с разметкой, ZIP-пакет |
| `processing/intake.py` | что считать `Failure`, а что — нестандартными данными (не позвоночник/бедро) |
| `processing/base.py`, `registry.py` | контракт процессора (`load()` / `predict()`), выбор через `PROCESSOR_BACKEND` |
| `processing/second_opinion.py` | второе мнение нейросети для бедра: ONNX замороженного DenseNet121 + логистическая регрессия, справочно |
| `processing/rulebased.py` + `processing/dxaqc/` | baseline на правилах: `image.py` (маски, единицы), `spine.py`, `femur.py` (измерения), `region.py` (область и сторона), `rules.py` (правила и объяснения), `thresholds.json` (пороги) |
| `models/`, `db/` | SQLAlchemy: Study → StudyImage → ImageResult; SQLite, добавление недостающих колонок без миграций |

Персональные данные в базе не хранятся — только технические теги. Исходные DICOM лежат
в томе; идентификаторы пациента попадают только в DICOM SR (читаются из файла в момент
выгрузки, чтобы отчёт встал в PACS).

### Frontend (`frontend/`)

React + Vite, раздаётся nginx, который же проксирует API. Загрузка файлов/папок/ZIP,
таблица исследований с фильтрами, пакетная обработка, карточка исследования: снимок с
разметкой (ось, контур бедра, ориентиры, посторонние предметы), все проверки с числами и
порогами, справочные проверки помечены, панель проверки врачом.

### ML (`ml/`)

| Модуль | Что делает |
|---|---|
| `dxa/inventory.py`, `labels.py`, `label_qc.py`, `build_dataset.py` | инвентаризация выгрузки, разбор и проверка разметки, сборка датасета с фолдами |
| `dxa/contact_sheet.py` | контактные листы для визуальной проверки |
| `dxa/arak.py` | подготовка Arak: снятие разметки сканера, приведение кадров, анонимизация имён |
| `baseline/featdump.py`, `calibrate.py` | измерения правил по выгрузке; калибровка порогов и OOF-метрики |
| `baseline/combine_check.py` | выбор способа сложения проверок в `quality_prob` вложенной CV |
| `baseline/localization.py` | Dice / IoU / расстояния между ключевыми точками |
| `train/model.py`, `dataset.py`, `tasks.py` | общий бэкбон + 7 голов, маскированный BCE с `pos_weight`, аугментации |
| `train/train.py` | обучение по фолдам (v1 и v2), продолжение после прерывания |
| `train/probe.py` | линейный зонд: замороженный бэкбон + логистическая регрессия |
| `train/pretrain.py` | предобучение бэкбона на Arak (регрессия BMD + область) |
| `train/compare.py`, `summary.py` | сравнение с правилами (парный бутстрэп), сводка и решение по правилу К2 |
| `train/metrics.py` | все метрики ТЗ — один код для правил и для моделей |
| `stage6_v2.sh` | этап 6 одной командой: окружение → датасет → правила → 3 конфигурации → сводка |

**Модель.** Одна сеть на обе области: общий бэкбон и 7 бинарных голов
(`spine_quality`, `spine_position`, `spine_axis`, `spine_foreign`, `femur_quality`,
`femur_position`, `femur_roi`). Лосс считается только по головам своей области (маска);
для снимков без известного вида нарушения (R3) головы нарушений выключены. Вход
384 × 320. Аугментации под смысл меток: для позвоночника без поворотов (угол оси — это
метка), для бедра поворот до 3°, горизонтальное отражение выключено (на нём держится
определение стороны).

### Развёртывание

`docker compose up --build` — два контейнера (backend, frontend), данные в томе.
Backend — один процесс uvicorn: очередь живёт внутри процесса. Тесты: backend 113,
ml 46 (включая тесты протокола обучения с torch), `ruff` чистый.

## 4. Baseline на правилах

### Как устроен

Каждое нарушение — порог на величине, измеренной по изображению в физических единицах
(с учётом анизотропного пикселя; без поправки углы завышались бы в 1.75 раза). У каждой
проверки есть источник порога: `ТЗ` (число прямо в ТЗ) или `разметка` (в ТЗ названа
проверка, но не число — подобран по разметке). Проверка либо **решающая** (формирует
`violation_type`), либо **справочная** (считается и показывается с порогом, но на
разметке не отделяет брак от нормы).

| Требование ТЗ | Что меряется | Порог | В вердикте |
|---|---|---|---|
| **Позвоночник** | | | |
| рис. 1, подвздошные кости в кадре | во сколько раз кость у нижнего края шире столба | 1.53 × (разметка) | да |
| рис. 1, верх — половина Th12 | число позвонков в кадре | > 8 (разметка) | справочно |
| рис. 2, ось до 5° | наклон хорды столба к вертикали, методика рисунка ТЗ | 5° (ТЗ) | справочно |
| рис. 2, рабочая версия | наклон по боковым границам столба | 1.88° (разметка) | да |
| рис. 2, сколиоз | излом оси между третями столба | 4.14° (разметка) | справочно |
| рис. 3, посторонние предметы | яркость тонких структур вне кости | 56.7 (разметка) | да |
| рис. 3, металл | площадь насыщенных объектов | > 0 px (ТЗ) | справочно (не разделяет) |
| **Бедро** | | | |
| рис. 4, седалищная кость | доля кости медиальнее бедра | 0.025 (разметка) | да |
| рис. 4, большой вертел | ширина кости на уровне вертела / диафиз | 1.45 × (разметка) | справочно |
| рис. 5, переротация / недоротация | выступ малого вертела / ширина диафиза | < 0.16 и > 0.70 | справочно |
| укладка диафиза вдоль оси | наклон диафиза | 4.96° (разметка) | да |
| рис. 6, 3 см сверху-снизу, 2 см по бокам | запасы поля от ROI проксимального отдела | 3 и 2 см (ТЗ) | справочно |
| рис. 6, рабочая версия | высота отсканированного поля | 26.99 см (разметка) | да |

Калибровка (`ml/baseline/calibrate.py`): пороги подбираются на четырёх фолдах, оценка —
на пятом; критерий — максимум balanced accuracy при специфичности ≥ 0.70, берётся центр
плато, а не точечный максимум; правило входит в вердикт, только если прибавляет ≥ 0.02 BA,
не больше 2 правил на нарушение. Финальные пороги — на всех данных, в
`thresholds.json`. Пересчёт из исходной выгрузки воспроизводит пороги и все 79 метрик
до знака.

`quality_prob`: для позвоночника — среднее по всем проверкам, включая справочные (выбрано
вложенной CV из четырёх вариантов: AUC 0.62 → 0.69, разница +0.07 [+0.01; +0.14]); для
бедра — максимум по решающим проверкам.

Особые исходы: `Failure` — файл не разбирается как DICOM; «нестандартные данные» — DICOM
открылся, но это не позвоночник/бедро (пустые область и класс); «структуры не найдены» —
вердикт «Некорректная укладка» с `quality_prob` 0.51 (в выгрузке — 2 файла из 502, одно
исследование; эксперт отметил именно это нарушение).

  полный путь от файла до вердикта — 43 мс на снимок, 502 из 502 файлов.
- Локализация. Точность на фантомах: Dice столба 0.983, IoU 0.967; ось позвоночника
  0.56 мм; ось диафиза 1.79 мм. Повторяемость на реальных снимках при сдвиге, шуме и
  повороте на 1°: Dice 0.974–0.995, смещения около 1 мм.
- Область определена верно на 246 из 246, сторона бедра — на 144 из 148.

### Два расхождения ТЗ с разметкой эксперта

1. **Ось до 5°:** порог ТЗ срабатывает на 4 снимках из 98, эксперт отметил 9 — и у всех
   девяти наклон 1.25–4.83°. Решает порог по разметке 1.88° (AUC 0.78), 5° — справочно.
   Вероятно, эксперт бракует сколиоз («сколиоз» в 29 комментариях).
2. **Поля 3 / 2 см:** буквальное правило бракует 108 снимков из 147 (73 %), эксперт — 6.
   Рамки ROI сканера в DICOM нет — мерить не от чего. Решает высота поля (AUC 0.87),
   3 / 2 см — справочно.

Слабее всего — **ротация бедра**: малый вертел локализуется на 86 % снимков, но разделяет
классы на уровне BA 0.59, поэтому ротация в вердикт не входит.

Подробно: [ml/baseline/REPORT.md](ml/baseline/REPORT.md).

## 5. Что пробовали с моделью и что это дало

Правила игры (К2 в [questions.md](questions.md)): конфигурации объявляются до запуска,
не больше четырёх, все отчитываются на тех же 5 фолдах; эпоха и порог по внешнему фолду
не выбираются; сравнение с правилами — попарно на тех же снимках, ДИ разницы AUC —
парный бутстрэп по исследованиям. Критерий этапа 6: macro-F1 выше правил на 0.05 хотя бы
в одной области при специфичности всех классов ≥ 0.70.

### 5.1. Линейный зонд — замороженная сеть (`train/probe.py`)

Бэкбон заморожен, признаки снимаются один раз, поверх — логистическая регрессия на каждую
задачу; регуляризация задана заранее, порог — вложенной CV тем же правилом, что у правил.
Считался на CPU до обучения, чтобы выбрать бэкбон.

| ROC AUC, OOF | Правила | XRV-DenseNet121, заморожен | XRV, случайные веса (контроль) |
|---|---:|---:|---:|
| Бедро: есть нарушение | 0.74 | 0.70 | 0.50 |
| Бедро: укладка | 0.68 | 0.67 | 0.58 |
| Бедро: область интереса | 0.87 | 0.80 | 0.69 |
| Позвоночник: ось | 0.78 | 0.39 | 0.60 |

**На бедре замороженная рентгеновская сеть вровень с правилами** (macro-F1 0.316 против
0.319), и это заслуга предобучения. На позвоночнике — нет: наклон оси — геометрия,
а глобальное усреднение признаков её теряет. Колонка ImageNet в том прогоне не
досчиталась (не было доступа к весам).

### 5.2. ResNet18, первый прогон (v1)

ImageNet, всё по умолчанию: 40 эпох, batch 16, AdamW 3e-4, косинусное расписание, оценка
по последней эпохе, порог 0.5. CPU, 2 ч 43 мин.

|---|---:|---:|---:|
| Позвоночник: есть нарушение | 0.69 | 0.69 | −0.00 [−0.15; +0.14] |
| Позвоночник: укладка | 0.68 | 0.81 | −0.13 [−0.43; +0.12] |
| Позвоночник: ось | 0.66 | 0.78 | −0.12 [−0.33; +0.07] |
| Позвоночник: посторонние предметы | 0.82 | 0.72 | +0.10 [−0.07; +0.28] |
| Бедро: есть нарушение | 0.72 | 0.74 | −0.03 [−0.16; +0.10] |
| Бедро: укладка | 0.70 | 0.68 | +0.01 [−0.14; +0.15] |
| Бедро: область интереса | 0.81 | 0.87 | −0.06 [−0.25; +0.16] |

### 5.3. Протокол v2 — три конфигурации (26.09)

Исправление переобучения, объявленное до прогона: число эпох выбирается по loss на
внутреннем фолде (k+1) mod 5 внутри train-части (максимум 40, остановка после 8 эпох без
улучшения), затем модель учится заново на всей train-части столько эпох; `pos_weight` —
только по обучающим снимкам; внешний фолд — только для предсказаний.

Конфигурации: `resnet18` (ImageNet), `xrv-densenet121`, `xrv-densenet121` после
предобучения на Arak. Все дообучаются **целиком** (все слои).

**Железо и сбой.** GTX 1660 Ti, 6 ГБ. Первый запуск дал loss = NaN с первой эпохи:
на этой карте cuDNN в fp16 возвращает NaN (проверено: свёртка 3×3 — NaN на всех
выходах; fp32 и fp16 без cuDNN — норма). fp32 не помещается: DenseNet121 требует больше
4.9 ГБ свободной памяти. Решение (дополнение к К2 от 26.09, до результатов): точность та
же, fp16, но cuDNN отключается, если пробная свёртка даёт NaN; NaN в loss останавливает
обучение сразу. Цена — скорость (шаг DenseNet121 1.8 с). Весь прогон — 3 ч 36 мин.

**Предобучение на Arak:** 1 669 снимков на обучение, 412 на контроль, 15 эпох, ~50 мин;
лучшая эпоха 10: область 98.5 %, корреляция BMD 0.80 (позвоночник) и 0.74 (бедро).

**Результат:**

| ROC AUC | Правила | resnet18 | xrv-densenet121 | xrv + Arak |
|---|---:|---:|---:|---:|
| Позвоночник: есть нарушение | 0.69 | 0.51 ▼ | 0.57 | 0.51 ▼ |
| Позвоночник: укладка | 0.81 | 0.59 | 0.63 | 0.58 |
| Позвоночник: ось | 0.78 | 0.61 | 0.44 ▼ | 0.54 |
| Позвоночник: посторонние предметы | 0.72 | 0.62 | 0.56 | 0.66 |
| Бедро: есть нарушение | 0.74 | 0.57 ▼ | 0.56 ▼ | 0.55 ▼ |
| Бедро: укладка | 0.68 | 0.60 | 0.57 | 0.52 ▼ |
| Бедро: область интереса | 0.87 | 0.86 | 0.50 ▼ | 0.67 |

▼ — правила сильнее статистически значимо (95% ДИ разницы целиком ниже нуля).

| macro-F1 | Правила | resnet18 | xrv-densenet121 | xrv + Arak |
|---|---:|---:|---:|---:|
| Позвоночник | 0.346 | 0.237 | 0.135 | 0.277 |
| Бедро | 0.319 | 0.348 (+0.03) | 0.151 | 0.223 |

Эпох на всей train-части по фолдам: resnet18 — 3, 7, 2, 3, 2; xrv-densenet121 — 2, 35,
23, 1, 1; xrv + Arak — 1, 29, 39, 3, 16.

**Критерий этапа 6 не прошла ни одна конфигурация.** Почему (по кривым обучения):

- **ResNet18** заучивает обучающие снимки за несколько эпох (фолд 1: train loss
  1.26 → 0.11 за 12 эпох), loss на внутренней проверке (~45 снимков) скачет 0.90–2.26 — ранняя
  остановка выбирает 2–7 эпох, модель не успевает научиться различать. Сеть при этом
  учится нормально — обход cuDNN ни при чём.
- **DenseNet121** при полном дообучении учится очень медленно (фолд 1: train loss
  1.14 → 0.86 за 40 эпох) — недообучен.
- **Предобучение на Arak** не помогло.
- Иронично, v1 без ранней остановки ранжировал лучше (AUC 0.69 / 0.72), но проигрывал
  по F1. На таком объёме результат определяется моментом остановки, а не
  способностью сети.

Перенастраивать эпохи или скорость обучения по этим цифрам нельзя — это подгонка под
те же фолды. Результат v2 честный: **на 246 снимках дообучаемая целиком сеть правила не
обгоняет.**

Все вопросы и решения — [questions.md](questions.md). Решения 23.09 приняты командой по
ТЗ и данным; ответ эксперта или заказчика главнее и меняет, как правило, одну строку в

**Эксперту:** Э1 — противоречивая строка 37 исключена; Э2 — пара бёдер с неразличимой

эндопротез оценивается как обычное бедро; Э9 — число позвонков справочно.

З7 — планируем на 246 снимках.

**Команде:** К1 — справочные проверки не входят в `violation_type`, но входят в
`quality_prob` позвоночника; **К2 — протокол обучения** (≤ 4 конфигураций заранее,
v2, правило выбора следующего шага; дополнение 26.09 про fp16); **К3 — гибрид: 4
варианта (только правила, только модель, среднее вероятностей, OR по нарушениям),
выбор вложенной CV**; К4 — соседние снимки в процессор не передаём; К5 — SR проверен
`dsrdump`, 7 нарушений стандарта исправлено; К6 — подпись врача — свободный текст;
К7 — данные и веса вне git, прогон пишет SHA-256 датасета.

## 7. Что сделано 24–28.09

**Сервис** (PR #1, коммит `f838641`):

- Повторная обработка больше не стирает решение врача: оно переносится на новый
  результат; статус пересчитывается относительно нового вердикта; если перенести нельзя
  — решение записывается в предупреждения исследования. Пока идёт обработка,
  проверка врачом запрещена (409).
- Поля ROI 3 / 2 см и ротация, которые не прошли отбор в вердикт, теперь показываются
  справочно (флаг `reference_when_off`), поля — с порогом ТЗ. Вердикты на 502 файлах и
  все метрики не изменились. До этого эти проверки не показывались вовсе.
- Повторная загрузка не создаёт дубликатов: известный SOPInstanceUID отклоняется, новые
  снимки существующего исследования добавляются к нему.

**Обучение** (коммит `06afb3c`):

- Автопроверка fp16 на видеокарте и отключение cuDNN при NaN; остановка обучения и
  предобучения на NaN; в `config.json` и `env.json` пишется, как считались свёртки.
- `ARAK_LIMIT` в пробном прогоне считает годные снимки, а не файлы.
- Полный прогон протокола v2 (раздел 5.3).

**Этапы 7–8** (коммит `a2867a4` и следующий):

- Гибрид по К3 с конфигурацией 4 (замороженный XRV-DenseNet121 + логистическая
  регрессия), объявленной до расчёта. Модель в вердикт не вошла (раздел 8).
- Второе мнение нейросети в сервисе для бедра: ONNX собирается из публичных весов при
  сборке образа, в сервисе — `onnxruntime` на CPU; признаки сервиса совпадают с
  признаками обучения на всех 246 снимках до 2·10⁻⁶.

**Подготовка к сдаче (этап 9):**

- Backend слушает только 127.0.0.1 (`BACKEND_BIND`), в README честно описано, где лежат
  данные пациента.
- Сайт загружает любое число файлов частями по 200; исследование собирается обратно.
- Таблица разметки (.xlsx) рядом со снимками больше не распаковывается в строки
  `Failure` — найдено прогоном всей выгрузки через Docker.
- Разметка сбрасывается при повторной обработке; повторный запуск в момент завершения
  предыдущего не теряется.
- Мелочи: описание Swagger, `null` вместо `Infinity` в `thresholds.json`, металл у
  позвоночника показывается справочно (по букве ТЗ), UID DICOM SR и вторичной серии
  одинаковы при повторном скачивании, повторная загрузка сломанного файла отклоняется.
- `make package` — пакет для целевой машины.
