# Densitometry AI — обзор проекта

Состояние на 28.09.2026. Единственный документ о проекте, кроме [README.md](README.md)
(запуск и API): цель, данные, архитектура, как принимается решение, метрики, всё, что
пробовали с ИИ-моделью, принятые решения, хронология, подготовка к сдаче, риски.

---

## 0. Коротко

- **Что это.** Сервис контроля качества DXA-исследований: принимает DICOM и по каждому
  снимку поясничного отдела позвоночника или проксимального отдела бедра говорит, годен
  ли он, какие нарушения укладки найдены и почему — с измеренной величиной и порогом
  рядом с каждым выводом.
- **Вердикт выносят правила ТЗ**: измерения по изображению + пороги. Out-of-fold на 246
  размеченных снимках: macro-F1 позвоночник **0.341**, бедро **0.319**; ROC AUC класса
  качества 0.69 и 0.74. Вердикт на 502 из 502 файлов выгрузки.
- **ИИ-модель правила не обогнала.** Пять заранее объявленных попыток и гибрид правил с
  лучшей моделью: ни одна не лучше правил. Причина — объём данных: 246 снимков, в редких
  классах 6–9 нарушений.
- **Модель в сервисе — вторым мнением.** Для бедра рядом с проверками правил —
  справочная оценка замороженного DenseNet121 с её точностью (AUC 0.70 / 0.67 / 0.80); в
  вердикт и выгрузку она не входит.
- **К сдаче готов.** Сервис прогнан в Docker по «Для теста» и по всей выгрузке: формат
  п. 2.5 без нарушений, Docker совпадает с локальным кодом на всех 502 снимках. Пакет для
  целевой машины — `make package`.
- **Что важно помнить.** Правила настроены на один сканер (GE Lunar Prodigy Advance);
  авторизации нет — только закрытый контур; главный рычаг качества — новые размеченные
  данные, а не архитектура.

## 1. Цель и требования ТЗ

### Задача

| Область | Что проверяется (раздел 2.3 ТЗ) | Закрытый список нарушений |
|---|---|---|
| Поясничный отдел позвоночника | укладка: внизу видны верхние края подвздошных костей, вверху — половина тела Th12 (рис. 1); ось позвоночника, наклон до 5° (рис. 2); нет посторонних предметов, артефактов, наложений (рис. 3) | «Некорректная укладка», «Не выравнена ось позвоночника», «Присутствуют посторонние предметы» |
| Проксимальный отдел бедра | видны большой вертел, шейка, седалищная кость (рис. 4); нет ротации — по малому вертелу: корректно / переротация / недоротация (рис. 5); область интереса с запасом 3 см сверху-снизу и 2 см справа-слева (рис. 6) | «Некорректная укладка», «Некорректная область интереса» |

### Выход (п. 2.5 ТЗ) — одна строка на снимок

```
path_to_study, study_uid, image_uid, anatomical_region, quality_class,
violation_type, processing_status, time_of_processing, quality_prob
```

- `quality_class` — целое 0/1; `processing_status` — `Success` / `Failure`;
  `time_of_processing` — секунды; несколько нарушений — через `;`.
- `quality_prob` — разрешён заказчиком дополнительно (ответ на вопрос 8).
- `anatomical_region` — два значения без проекции (ответ на вопрос 15), сторона бедра в
  выгрузку не входит.
- `Failure` — только если файл не открывается или не разбирается как DICOM (ответ
  заказчика 23.09).

### Технические требования

- До 3 изображений в исследовании, не больше 3 минут на исследование.
- Воспроизводимость (один файл — один вердикт), независимость от персональных тегов.
- Дополнительно: DICOM SR и дополнительные серии, коррекция разметки с подтверждением
  специалиста.
- Метрики: классификация (Se, Sp, BA, F1, ROC/PR AUC, macro-F1), локализация (Dice, IoU,
  расстояние между ключевыми точками), пропускная способность.
- Закрытый тест: папка «Для теста», целевая машина 2 × H200, 44 CPU, 256 ГБ.

## 2. Данные

### 2.1. Выгрузка заказчика (`Densitometry_data/НД_для_обучения`)

| | |
|---|---|
| исследований | 100 |
| файлов DICOM | 499 (+ 3 в «Для теста»; всего 502) и таблица `разметка.xlsx` |
| уникальных снимков после дедупликации по пикселям | 252 (позвоночник 99, бедро 153) |
| размечено и годно для обучения | **246**: позвоночник 98, бедро 148 |
| состав исследования | позвоночник + два бедра — 74, только позвоночник — 21, позвоночник + одно бедро — 4, только бедро — 1 |
| сканер | GE Lunar Prodigy Advance, CR, 8 бит, MONOCHROME2, 233–405 × 248–300 px |

Особенности, из-за которых пришлось принимать решения:

- **Дубли.** Один снимок лежит в исследовании 2–5 раз с разными SOPInstanceUID и
  одинаковыми пикселями (в исследовании из 13 файлов — 3 снимка). Дедупликация по md5
  пикселей, иначе один кадр попал бы и в обучение, и в проверку.
- **Пустые теги** `BodyPartExamined`, `ViewPosition`, `Laterality`, нет `PixelSpacing`.
  Область определяется по ширине кадра (300 px — позвоночник, 280/248 px — бедро,
  промежуточных нет), сторона бедра — по положению диафиза (у правого уходит влево),
  пиксель 1.05 × 0.60 мм (данные заказчика; без поправки на анизотропию углы завышались бы
  в 1.75 раза).
- **Разметка ссылается на имя папки (`2.25.*`), а не на StudyInstanceUID в тегах
  (`1.2.643.*`)** — совпадений ноль, join только по имени папки.
- **Разметка на уровне исследования**, а оценивается снимок: для бедра метка зависит от
  правильно определённой стороны (у 14 из 72 исследований метки бёдер различаются).
- Данные пациента в тегах обезличены (`Anonymized`), поэтому группировка — по
  исследованию. Похожих снимков между разными исследованиями не найдено.
- UID сканера формально нарушают стандарт (компоненты с ведущим нулём) — pydicom
  предупреждает, на работу не влияет.

### 2.2. Разметка и её проверка

Один лист, одна строка на исследование, значения 0/1: для позвоночника — укладка, ось,
посторонние предметы и итог; для каждого бедра — позиционирование/ротация, ROI и итог.
Компоненты один в один ложатся на закрытые списки заказчика.

`ml/dxa/label_qc.py` проверяет разметку до сборки датасета. Исходный `разметка.xlsx` не
меняется. Исправляется только то, для чего есть проверяемое основание в самих данных;
если два поля эксперта противоречат друг другу, строка исключается и уходит на ручную
проверку.

| Правило | Что | Основание |
|---|---|---|
| R1 | нормализация значений | смысл не меняется |
| R2 | итог пуст, компоненты есть → итог = максимум компонентов | итог — сводка компонентов; равенство в 246 из 249 областей |
| R3 | итог = 1, все компоненты 0 → класс 1, **вид нарушения неизвестен** | заключение эксперта сохраняется, вид нарушения не выдумывается: головы нарушений маскируются |
| R4 | итог = 0, но компонент = 1 → **исключить** | поля спорят о классе, выбрать можно только догадкой |
| R5 | значение вне {0, 1} → пусто | |
| R6 | повтор исследования → исключить | непонятно, какая строка актуальна |
| R7 | разметка без снимка — отбросить; снимок без разметки — не учить | |
| R8 | один снимок бедра и размечена одна сторона → сторона из разметки | эксперт размечал тот снимок, который есть |
| R9 | пара бёдер с неразличимой стороной: метки разные — исключить обе, одинаковые — оставить | при одинаковых метках перестановка ничего не меняет |

Итог: 249 строк «исследование × область», годных 248, без вида нарушения (R3) — 2,
исключено по противоречию (R4) — 1, автоисправлений — 4, на ручную проверку — 4 (строки
37, 71, 8, 13 — см. Э1–Э3). Журнал правок и спорные места — `ml/qc_sample/`.

фолдов и меток `83c5b71b42235551…` проверяется перед каждым обучением.

## 3. Архитектура

### 3.1. Схема

```
браузер ──► nginx (frontend, :8080) ──► FastAPI (backend, 127.0.0.1:8000)
                                          │
              загрузка ─► UploadService ──┤ группировка по StudyInstanceUID, документы —
                                          │ мимо, не-DICOM → строка Failure, без дублей
                                          ▼
                                   SQLite + файлы (том densitometry-data)
                                          │
        «Обработать» ─► TaskRunner (потоки в процессе API)
                                          │
                                          ▼
                                     pipeline ─► intake (заголовок DICOM:
                                          │       Failure / нестандартные данные)
                                          ▼
                                     rulebased: измерения ─► правила ─► вердикт
                                          │        └─► второе мнение (бедро, ONNX)
                                          ▼
                     результат: CSV / XLSX / DICOM SR / ZIP-пакет / PNG с разметкой
                     + проверка врачом (решение хранится отдельно от вердикта сервиса)
```

### 3.2. Backend (`backend/app/`)

| Модуль | Что делает |
|---|---|
| `main.py` | приложение FastAPI, Swagger без интернета, перезапуск прерванных задач при старте |
| `api/routes/` | `studies` (загрузка, статус, результат, выгрузки, превью, разметка, проверка врачом), `batch`, `health` |
| `services/upload.py` | потоковая загрузка файлов и ZIP; документы (в том числе .xlsx/.docx) пропускаются до распаковки; дубли — по SOPInstanceUID, а у нераспознанных файлов — по содержимому и имени; новые снимки существующего исследования добавляются к нему |
| `services/pipeline.py` | обработка по снимкам, прогресс, лимит 180 с; при повторной обработке решение врача переносится, старая разметка стирается |
| `services/task_runner.py` | пул потоков; повторный запуск в момент завершения предыдущего не теряется; заменяется на Celery/RQ без изменения остального |
| `services/review.py` | подтверждение / исправление врачом по тому же закрытому списку; перенос решения при повторной обработке |
| `services/export.py` | CSV/XLSX по п. 2.5 и листы `checks`, `review` |
| `services/dicom_sr.py`, `package.py`, `overlay.py` | Comprehensive SR (проверен `dsrdump`), вторичная серия с разметкой, ZIP-пакет; UID из содержимого |
| `processing/intake.py` | что считать `Failure`, а что — нестандартными данными |
| `processing/base.py`, `registry.py` | контракт процессора (`load()` / `predict()`), выбор через `PROCESSOR_BACKEND` (`rulebased`, `mock`) |
| `processing/rulebased.py` + `processing/dxaqc/` | правила: `image.py` (маски, единицы), `spine.py`, `femur.py` (измерения), `region.py` (область и сторона), `rules.py` (правила и объяснения), `thresholds.json` (пороги) |
| `processing/second_opinion.py` | второе мнение: ONNX замороженного DenseNet121 + логистическая регрессия (`second_opinion_model/xrv_probe.json`) |
| `scripts/export_second_opinion.py` | экспорт сети в ONNX (запускается при сборке образа) |
| `models/`, `db/` | SQLAlchemy: Study → StudyImage → ImageResult; SQLite, недостающие колонки добавляются без миграций |

### 3.3. Frontend (`frontend/`)

React + Vite, раздаётся nginx, который же проксирует API. Загрузка файлов, папок и ZIP
(большая папка — частями по 200 файлов), таблица исследований с фильтрами, пакетная
обработка, карточка исследования: снимок с разметкой, все проверки с числами и порогами
(справочные помечены), оценка ИИ-модели для бедра, панель проверки врачом.

### 3.4. ML (`ml/`)

| Модуль | Что делает |
|---|---|
| `dxa/inventory.py`, `labels.py`, `label_qc.py`, `build_dataset.py`, `contact_sheet.py` | инвентаризация выгрузки, разбор и проверка разметки, сборка датасета с фолдами, листы для проверки глазами |
| `dxa/arak.py` | подготовка открытого набора Arak |
| `baseline/featdump.py`, `calibrate.py` | измерения правил по выгрузке; калибровка порогов и OOF-метрики |
| `baseline/combine_check.py` | выбор способа сложения проверок в `quality_prob` (вложенная CV) |
| `baseline/localization.py`, `rank_features.py` | Dice / IoU / ключевые точки; разделяющая способность признаков |
| `train/model.py`, `dataset.py`, `tasks.py`, `metrics.py` | модель, датасет, задачи, все метрики ТЗ (один код для правил и моделей) |
| `train/train.py`, `pretrain.py` | обучение по фолдам (протоколы v1 и v2), предобучение на Arak |
| `train/probe.py` | линейный зонд: замороженная сеть + логистическая регрессия |
| `train/compare.py`, `summary.py` | сравнение с правилами (парный бутстрэп), сводка и решение по правилу К2 |
| `train/hybrid.py` | этап 7: гибрид правил и модели, вложенная CV |
| `train/second_opinion.py` | коэффициенты второго мнения для сервиса и сквозная сверка с ним |
| `stage6_v2.sh` | этап 6 одной командой на GPU |

**Модель для обучения.** Одна сеть на обе области: общий бэкбон и 7 бинарных голов
(качество и виды нарушений каждой области). Лосс — маскированный BCE с `pos_weight`:
считается только по головам своей области, а для снимков без известного вида нарушения
(R3) головы нарушений выключены. Вход 384 × 320. Аугментации под смысл меток: для
позвоночника без поворотов (угол оси — это метка), для бедра поворот до 3°, отражение
выключено (на нём держится определение стороны).

### 3.5. Развёртывание

`docker compose up --build` — два контейнера (backend, frontend), данные в томе. Backend —
один процесс uvicorn, очередь внутри процесса. Образ backend (797 МБ) содержит ONNX
второго мнения: стадия сборки с torch экспортирует его из публичных весов, в итоговый
образ torch не попадает. Тесты: backend 129, ml 55, в контейнере — `make test-docker`.

## 4. Как принимается решение

### 4.1. Проверки

Каждое нарушение — порог на величине, измеренной по изображению в физических единицах.
Источник порога — `ТЗ` (число прямо в ТЗ) или `разметка` (в ТЗ названа проверка, но не
число). Проверка либо **решающая** (формирует `violation_type`), либо **справочная**
(считается и показывается с порогом, но на разметке не отделяет брак от нормы).

| Требование ТЗ | Что меряется | Порог | В вердикте |
|---|---|---|---|
| **Позвоночник** | | | |
| рис. 1, подвздошные кости в кадре | во сколько раз кость у нижнего края шире столба | 1.53 × (разметка) | да |
| рис. 1, верх — половина Th12 | число позвонков в кадре | > 8 (разметка) | справочно |
| рис. 2, ось до 5° | наклон хорды столба к вертикали, методика рисунка ТЗ | 5° (ТЗ) | справочно |
| рис. 2, рабочая версия | наклон по боковым границам столба | 1.88° (разметка) | да |
| рис. 2, сколиоз | излом оси между третями столба | 4.14° (разметка) | справочно |
| рис. 3, посторонние предметы | яркость тонких структур вне кости | 56.7 (разметка) | да |
| рис. 3, металл | площадь насыщенных объектов вне кости | > 0 px (ТЗ) | справочно |
| **Бедро** | | | |
| рис. 4, седалищная кость | доля кости медиальнее бедра | 0.025 (разметка) | да |
| рис. 4, большой вертел | ширина кости на уровне вертела / диафиз | 1.45 × (разметка) | справочно |
| рис. 5, переротация / недоротация | выступ малого вертела / ширина диафиза | < 0.16 и > 0.70 | справочно |
| укладка диафиза вдоль оси | наклон диафиза | 4.96° (разметка) | да |

Методика оси выведена из рисунка 2 ТЗ: он извлечён из PDF и измерен по пикселям — одна
линия строго вертикальна, вторая идёт по столбу, вершина угла внизу. Отсюда
`axis_tz_deg` — угол хорды «низ столба → верх столба» к вертикали. Рабочая оценка того же
наклона по боковым границам столба устойчивее к обрезке кадра и лучше разделяет разметку
(AUC 0.78 против 0.70). Контроль: поворот снимка на известный угол меняет измерение на ту
же величину с точностью ~1°.

### 4.2. Калибровка порогов (`ml/baseline/calibrate.py`)

- Пороги подбираются на четырёх фолдах, оценка — на пятом; все метрики — out-of-fold.
- Критерий — максимум balanced accuracy при специфичности ≥ 0.70; берётся центр плато
  сглаженной кривой, а не точечный максимум, который на полусотне примеров «гуляет».
- Правило входит в вердикт, только если прибавляет ≥ 0.02 BA, не больше двух правил на
  нарушение: иначе жадный отбор подгоняется под обучающий фолд.
- Проверку ТЗ, которую отбор не взял в вердикт (ротация, поля 3/2 см, металл), калибровка
  не выключает, а оставляет справочной — с порогом ТЗ, где он есть (флаг
  `reference_when_off`).
- Финальные пороги — на всех данных, в `thresholds.json`. Пересчёт из исходной выгрузки
  воспроизводит пороги и все 79 метрик до знака.

### 4.3. `quality_prob`

Для позвоночника — среднее по всем проверкам, включая справочные (выбрано вложенной CV из
четырёх заранее объявленных вариантов: AUC класса качества 0.62 → 0.69, разница +0.07
[+0.01; +0.14]); для бедра — максимум по решающим (вложенная CV выигрыша не показала).
Справочные проверки, которые калибровка «разжаловала», в сложение не входят (флаг
`in_score`). `quality_prob` > 0.5 тогда и только тогда, когда `quality_class` = 1.

### 4.4. Особые исходы

- **`Failure`** — файл не открывается или не разбирается как DICOM (включая пустой файл
  и недекодируемые пиксели). Такой файл не отбрасывается: у него есть строка с причиной.
  Служебные файлы (DICOMDIR, .DS_Store, __MACOSX) и документы строки не получают.
- **Нестандартные данные** — DICOM открылся, но это не позвоночник и не бедро: нет
  изображения, модальность CT/MR/SR и т. п., другая часть тела в тегах, цветной кадр,
  кадр больше 1024 или меньше 60 px, не похож на снимок денситометра, нет кости. `Success`,
  область, класс и `quality_prob` пустые, причина видна на сайте и в SR. На выгрузке не
  срабатывает ни разу.
- **Структуры не найдены** — кость есть, но бедро не разбирается на диафиз и вертелы или
  не выделяется столб: «Некорректная укладка» с `quality_prob` 0.51. На выгрузке — одно
  исследование (2 файла), и эксперт отметил именно это.


### 4.5. Второе мнение ИИ-модели

Для снимка бедра — три справочные строки «Оценка ИИ-модели» (есть нарушение, укладка,
область интереса): 0.5 и выше — ИИ-модель видит нарушение, рядом — её точность на
отложенных данных. На `violation_type`, `quality_class`, `quality_prob` и выгрузку по
п. 2.5 не влияет; на позвоночнике не показывается (там модель почти случайна). Как
получена и проверена — раздел 6.6. Выключается `SECOND_OPINION=false`; если файлов
модели нет, сервис работает без неё.

### 4.6. Проверка специалистом

Под каждым снимком — «Подтвердить» и «Исправить». Исправление ограничено тем же
закрытым списком нарушений своей области. Автоматический вердикт **не переписывается**:
решение врача хранится в отдельных полях, поэтому видно, что предложил сервис и что решил
человек, а метрики модели не оказываются посчитанными по правкам человека.

- Выгрузка по умолчанию — вердикт сервиса; решение врача — `?source=reviewed`; в XLSX
  обе версии рядом на листе `review`.
- Повторная обработка решение врача не стирает: оно переносится на новый результат. Если
  новый вердикт совпал с решением врача — «подтверждено», если нет — «исправлено», решение
  то же. Перенести нельзя, только если снимок теперь не обработался или область другая —
  тогда решение записывается в предупреждения исследования. Пока исследование в очереди
  или обрабатывается, проверка запрещена (409).
- Имя проверившего попадает в SR как VerifyingObserverName; VERIFIED ставится, только
  если имя указано. Подпись врача сервис не удостоверяет.

### 4.7. Выгрузки

- **CSV / XLSX** по п. 2.5; в XLSX ещё `checks` (по строке на проверку: измерено,
  критерий, порог ТЗ, вердикт по букве ТЗ, участвует ли в вердикте) и `review`.
- **DICOM SR** — Comprehensive SR: область, класс, нарушения, все проверки как NUM с
  единицами UCUM, координаты найденных структур. Идентификаторы пациента читаются из
  исходного файла в момент выгрузки, иначе отчёт не встанет в PACS к нужному
  исследованию. UID — из содержимого: повторное скачивание не плодит копий в PACS, новое
  решение врача даёт новый экземпляр в той же серии. Проверен `dsrdump` (dcmtk), найденные
  7 нарушений стандарта исправлены.
- **ZIP-пакет** — SR, вторичная серия Secondary Capture с разметкой, CSV и XLSX.

### 5.4. Два расхождения ТЗ с разметкой эксперта

1. **Ось до 5°.** Порог ТЗ срабатывает на 4 снимках из 98, эксперт отметил 9 — и у всех

   5° — справочно. Вероятно, эксперт бракует сколиоз («сколиоз» — в 29 комментариях):
   излом оси между третями больше 5° у 6 из 25 снимков с почти нулевым суммарным наклоном.
2. **Поля 3 / 2 см.** Буквальное правило (от ROI проксимального отдела, как на рис. 6)
   бракует 108 снимков из 147 (73 %), эксперт — 6. Боковой запас упирается в ширину кадра:
   поле 12.5 см при ROI 4.7 см. Решает высота поля (21.3 см против 27.4 см в норме, AUC

### 5.5. Предел подхода

Слабее всего — **ротация бедра**. Малый вертел локализуется на 86 % снимков (медиана
выступа 7.1 мм), но разделяет классы на уровне BA 0.59: порог плохо отделяет бугорок от
шейки на низком контрасте. Если вертел не найден, правило ротации молчит, а не выдаёт
ложное нарушение. Модель эту проблему не закрыла; нужна разметка (Э5).

### 6.4. Протокол v2 — три конфигурации (26.09)

Объявлен до прогона: эпоха по loss на внутреннем фолде (k+1) mod 5 внутри train-части
(максимум 40, остановка после 8 эпох без улучшения), затем обучение на всей train-части
столько эпох; `pos_weight` — только по обучающим снимкам; внешний фолд — только для
предсказаний. Конфигурации: `resnet18` (ImageNet), `xrv-densenet121`, `xrv-densenet121`
после предобучения на Arak. Все дообучаются целиком.

**Железо.** GTX 1660 Ti (6 ГБ). cuDNN в fp16 на этой карте возвращает NaN (свёртка 3×3 —
NaN на всех выходах), а fp32 для DenseNet121 не помещается в память. Решение до
результатов: точность fp16 по протоколу, свёртки без cuDNN — это определяется пробной
свёрткой автоматически; NaN в loss останавливает обучение. Прогон — 3 ч 36 мин.
Предобучение на Arak: 1 669 / 412 снимков, 15 эпох, лучшая 10 — область 98.5 %,
корреляция BMD 0.80 (позвоночник) и 0.74 (бедро).

### 6.5. Гибрид (этап 7, 27.09)

Резервная конфигурация 4 — замороженный XRV-DenseNet121 + логистическая регрессия,
объявлена до расчёта (К2). Варианты К3 — только правила, среднее, OR, только модель —
выбирались вложенной CV по области, по macro-F1 видов нарушений; при равенстве —
правила. «Ось позвоночника», где правила объективно сильнее, во всех вариантах за
правилами (`python -m train.hybrid`, полторы минуты на CPU).

|---|---:|---:|
| Только правила | 0.346 | 0.319 |

### 6.6. Второе мнение (этап 8, 28.09)

Конфигурация 4 без изменений, только бедро. Регрессия обучена на всех 148 снимках бедра

Сквозная проверка (`--check`): исходные DICOM через код сервиса против признаков, на
которых училась регрессия, на всех 246 снимках — разница признаков не больше 1.9·10⁻⁶,
косинус 1.000000, оценки — не больше 3.1·10⁻⁶. На снимках обучающей выгрузки оценки
уверенные (регрессия их видела); честная точность — только OOF.

## 7. Решения и вопросы

Вопросы к эксперту (Э), заказчику (З) и команде (К). 23.09 на все приняты решения —
командой, по ТЗ и данным. Правила: разметку по догадке не меняем, медицинских критериев
сверх ТЗ не вводим, каждое решение, меняющее результат, проверено на отложенных фолдах.
Если эксперт или заказчик ответит иначе, его ответ главнее, и меняется, как правило,
одна строка в `thresholds.json`.

### Эксперту

- **Э1. Строка 37: итог «годно», отмечено «не выравнена ось», комментарий «перелом».**
  Строка исключена: выбрать одно из полей — исправить разметку по догадке. Перелом в ТЗ не
  критерий укладки. 1 снимок из 98.
- **Э2. Строка 71: какое бедро правое.** Диафизы почти по центру, метки разные — оба снимка
  исключены. 2 из 148.
- **Э3. Строки 8 и 13: брак без отмеченного нарушения («сколиоз»).** Вид нарушения не
  дописываем; снимки участвуют только в классе качества.
- **Э4. Ось при сколиозе — главный вопрос.** Все 9 отмеченных снимков по букве ТЗ в норме.
  Решает наклон по границам столба с порогом 1.88° из разметки; 5° и излом оси —
  справочно. Нужен измеримый критерий эксперта.
- **Э5. Разметить ротацию бедра тремя значениями на 50–100 снимках.** Сами не размечаем;
  ротация справочно. Это дало бы больше, чем любая доработка алгоритма.
- **Э6. Наклон диафиза как причина «некорректной укладки».** Оставлен решающим: это часть
  стандартной укладки бедра при DXA, AUC 0.67, порог 4.96°. Единственный решающий
  критерий не из текста ТЗ, отключается одним флагом.
- **Э7. Что такое «выраженный» посторонний предмет.** Яркость тонких структур вне кости
  выше 56.7 (Se 0.47, Sp 0.79, AUC 0.71). Площадь металла — справочно, по букве ТЗ.
- **Э8. Бедро с эндопротезом.** Эксперт такие бёдра не размечал — оцениваются как обычные;
  металл на них измеряется (1.5–11 тыс. px), пометка добавляется одним правилом.
- **Э9. Верхний уровень «половина Th12».** Число позвонков — справочно, входит в
  `quality_prob` позвоночника.

### Заказчику

- **З1. От чего отсчитываются поля 3 и 2 см.** Рамки ROI сканера в DICOM нет; буквальное
  правило бракует 73 %. Справочно; решает высота поля (AUC 0.87).
- **З2. Данные анализа из программы сканера.** Работаем только с изображениями;
  локализация — на фантомах и по повторяемости, так и подписано.
- **З3. Как считается итоговая оценка и `Failure`.** Ответ заказчика 23.09: `Failure` —
  только не-DICOM; нестандартные снимки — `Success` без области; «структуры не найдены» —
  вердикт. Итог — вердикт на 502 из 502.
- **З4. Что дороже — пропуск брака или ложная тревога.** Специфичность ≥ 0.70; строже —
  хуже (раздел 5.1).
- **З5. Проекция.** Не выдаём: вопрос 15 задал два значения области без проекции.
- **З6. Ответы на вопросы 2–5, 7, 9–14 первого списка** не найдены; всё нужное решено здесь.
- **З7. Будут ли ещё размеченные данные.** Планируем на 246 снимках; новые данные — главный
  рычаг (раздел 11).

### Команде

- **К1. Справочные проверки.** В `violation_type` не входят (иначе macro-F1 позвоночника
  0.341 → 0.223), но входят в `quality_prob` позвоночника (+0.07 AUC).
- **К2. Протокол обучения.** Не больше четырёх конфигураций, объявленных заранее, все в
  отчёте на тех же пяти фолдах; один фолд не откладывается (в редких классах осталось бы
  1–2 примера). Протокол v2 и правило выбора следующего шага — объявлены до прогона.
  Дополнение 26.09: fp16 без cuDNN на GTX 16xx. Дополнение 27.09: резервная конфигурация
  4 (замороженный XRV + логистическая регрессия) под гипотезу «полное дообучение
  переобучается» — взята из кривых обучения, а не из разбора расхождений глазами, как
  требовало правило; это отступление записано, цифры конфигурации 4 оптимистичны
  (результат зонда был известен). ResNet18 в гибрид не пошёл: для чистой вложенной CV
  нужны 20 дополнительных обучений. Результат и этап 8 — разделы 6.5–6.6.
- **К3. Как склеивать правила и модель.** Четыре варианта, выбор вложенной CV; вариант
  «модель — арбитр, где правило неуверено» не рассматривается: нужен ещё один порог на тех
  же 6–9 позитивах.
- **К4. Сторона бедра на одиночном снимке.** Соседние снимки не передаём: на 4 расхождениях
  из 148 вердикт одинаков при обеих сторонах.
- **К5. Проверка в PACS.** SR проверен `dsrdump`, вторичная серия — `dcmdump`; загрузить в
  PACS клиники перед сдачей всё равно нужно.
- **К6. Подпись врача.** Для закрытого контура — свободный текст; авторизация вне ТЗ.
- **К7. Где хранить данные и веса.** Вне git: выгрузка рядом с репозиторием, датасет —
  `ml/data/`, прогоны — `ml/runs/`; каждый прогон пишет SHA-256 датасета. Для второго
  мнения в git только коэффициенты регрессии (140 КБ), сеть — публичные веса, собирается
  при сборке образа. Если репозиторий публичный — нужно согласие заказчика: коэффициенты
  обучены на его снимках.

## 10. Риски и ограничения

| Риск | Что с ним |
|---|---|
| Привязка к одному сканеру | Область — по ширине кадра, пиксель — константа, пороги яркости — под 8 бит GE Lunar; на другом аппарате правила сломаются тихо. Закрытый тест, по всему, с того же аппарата |

## 12. Как воспроизвести

```bash
# сервис
docker compose up --build                     # http://localhost:8080, Swagger — /docs
make test                                     # тесты backend и ml
make test-docker                              # тесты backend в контейнере
make smoke                                    # загрузка → обработка → выгрузка на запущенном сервисе
make package                                  # пакет для сдачи в dist/

# данные (из папки ml/)
python -m dxa.build_dataset --data-root /путь/к/Densitometry_data --out data/processed
python -m dxa.contact_sheet --data data/processed --out qa

# правила
python baseline/featdump.py --data data/processed --out /tmp/features.csv
python baseline/calibrate.py --features /tmp/features.csv    # пороги + OOF-метрики
python baseline/combine_check.py --features /tmp/features.csv
python baseline/localization.py                              # Dice / IoU / ключевые точки

# модели
bash stage6_v2.sh /путь/к/Densitometry_data   # этап 6 на GPU -> runs/v2/SUMMARY.md
python -m train.probe --data data/processed   # линейный зонд, CPU, минуты
python -m train.hybrid                        # этап 7 -> runs/hybrid/HYBRID.md
python -m train.second_opinion                # коэффициенты второго мнения для сервиса
python -m train.second_opinion --check /путь/к/Densitometry_data   # сверка сервиса с обучением
```

Результаты прогонов (`ml/runs/`, `ml/data/`) в git не входят: сводки, предсказания и
метрики там, веса дообученных сетей удалены — они пересобираются той же командой.
